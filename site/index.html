Leanwork SDD · v2.2.0

Do briefing ao review, sem perder o fio.

Um pipeline Spec-Driven Development em seis skills coordenadas: arquitetura, requisitos, interface, plano, execução e review. Cada artefato declara seus elos por ID, cada commit carrega o trailer Refs:, e a verificação não depende de o agente lembrar dela.

O pipeline

Seis fases,
uma cadeia só.

A execução é uma fase do pipeline, não um intervalo entre fases. As fases 5 e 6 se alternam fatia a fatia até o plano fechar. O estado vive no plano; a trilha de quando e em que commit, no git.

context-leanwork — transversal ao pipeline inteiro, sempre opt-in. Gera o CLAUDE.md da raiz e dos módulos, mais o .claude/settings.json de permissões. Em projeto .NET, oferece o catálogo de segurança e desempenho — adotado só com aceite. Nunca automático, nunca destrutivo.

Trilha rápida — mudança com menos de três arquivos e nenhuma porta de mão única (migration, contrato público, schema, permissão) vira um plano de uma tarefa, com os cenários dentro dela. Encurta o planejamento, não a verificação: execução, review e gates são os mesmos.

O loop de execução

Um estado,
uma fonte.

O campo Status: da tarefa é o único estado — o plano não guarda histórico. Quando e em que commit cada tarefa mudou vem do git log, pelo trailer Refs:.

Pendente

Tarefa aguardando. Elegível quando todas as dependências estiverem concluídas.

Em andamento

Marcado antes da primeira linha de código. É o que torna a sessão recuperável.

Concluído

Critérios de aceite atendidos, typecheck limpo e suíte verde. Nunca com teste vermelho.

Bloqueado

Motivo no campo Bloqueio:. É também para onde um finding bloqueante do review devolve a tarefa.

/leanwork-execute T-04

  1. Abre a branch task/PLAN-001-T-04 a partir da base
  2. Confere com validate_ids.py que cada ID citado existe — senão, para e reporta
  3. Carrega o PRD, a arquitetura e a SPEC-UI nos IDs que a tarefa declara
  4. Escreve o teste na costura antes do código de produção
  5. Roda typecheck e build antes da suíte
  6. Fecha o estado, commita na branch com Refs: T-04, CA-01 e encadeia o review

review encadeado · /leanwork-review T-04 no round seguinte

  1. Despacha um sub-agente sem o raciocínio de quem implementou, com só o diff da branch
  2. Avalia os seis eixos com evidência de arquivo e linha
  3. Injeta defeitos no código novo para ver se os testes pegam
  4. Emite R-01..R-XX; o hook valida o relatório ao gravar
  5. Finding bloqueante devolve a tarefa para Bloqueado, com o motivo em Bloqueio:; sem ele, a branch entra na base com merge --no-ff

Quem implementou não decide se a implementação passou: o /leanwork-execute encadeia o review num sub-agente que não viu a implementação, e só transcreve o veredicto que volta.

A verificação

Sai a coreografia,
fica a verificação.

Modelos atuais seguem instrução concisa, mas continuam declarando conclusão sem prova e escrevendo teste raso. A 2.0.0 cortou o que era cerimônia e manteve intacto o que pega erro.

Gate

Disparado por hook

Gravou em docs/plans/ ou docs/reviews/, o validador roda. Reprovação volta ao modelo, que corrige antes de apresentar.

Review

Autor ≠ verificador

O review roda num sub-agente de contexto limpo. Quem recebe a justificativa julga se ela convence, não se o código cumpre o spec.

Teste

Sensor de discriminação

Um defeito é injetado no código novo, em scratch. Se a suíte continua verde, o teste não pega o bug — e isso é bloqueante.

Cobertura

Evidência ou zero

Cenário só conta como coberto com arquivo:linha e a asserção reproduzida. Nome de método de teste não é prova.

Git

Trilha no commit

Todo commit de tarefa termina com Refs: T-XX, CA-XX, conferido pelo check_commit.py — também como hook commit-msg.

Matriz

Gerada por script

status.py e trace.py leem os artefatos e o git de forma determinística. O modelo só interpreta as lacunas.

Código

Projeto sem interface pula a fase 3 inteira, e as colunas de UI somem da matriz — ausência não vira gap. O elo código → requisito vem do trailer de cada commit, e a matriz sai do trace.py. Lacuna declarada vale mais que lacuna preenchida: nenhuma skill inventa para fechar a matriz.

As skills

O que cada
fase produz.

Todas stack-agnósticas, com regras pinadas no topo e entrevista que busca no repositório antes de perguntar — um bloco por rodada, com recomendação em cada decisão.

Os comandos

Quatro pontos
de entrada.

Cada comando pré-aprova leitura mais a pasta do artefato que ele mesmo produz. Bash só é pré-autorizado para rodar os gates em Python.

ComandoO que faz
/leanwork-pipelinePonto de entrada: conduz o início (fluxo completo ou trilha rápida) ou lê o estado e sugere a próxima ação
/leanwork-executeExecuta uma tarefa na sua branch, carregando o contexto declarado, encadeia o review e integra na base sem finding bloqueante
/leanwork-reviewRevisa uma tarefa num sub-agente de contexto limpo, sobre o diff da branch. Finding bloqueante volta como Status: Bloqueado; usado direto no round seguinte
/leanwork-traceGera a matriz ADR ↔ RN ↔ CA ↔ UI ↔ T ↔ R e aponta os gaps
/leanwork-sdd:<skill>Chama uma skill direto — ex.: prototype-leanwork, context-leanwork
O review

Seis eixos,
com evidência.

Os eixos 1 a 5 aplicam sempre. O eixo 6 só entra quando o projeto tem SPEC-UI e a tarefa é de interface. Cada finding cita arquivo e linha — sem achismos.

01

Aderência ao plano

A tarefa T-XX foi entregue como prometida? Porta de mão única não declarada é bloqueante; arquivo extra não é finding.

02

Rastreabilidade

Os commits trazem o trailer Refs:? Testes e código preservam os IDs que amarram o trabalho ao requisito?

03

Aderência ao spec

Cada RN foi concretizada, cada CA tem teste e cada ADR foi respeitada?

04

Cobertura de teste

Os testes existem e pegariam o bug? Asserção rasa não cobre; mutante sobrevivente é bloqueante.

05

Qualidade do código

O que o CLAUDE.md do projeto declara, mais um piso de segurança: segredo no código e dado pessoal em log. Projeto .NET pode adotar o catálogo de segurança e desempenho, e cada item vira critério.

06

Conformidade de interface

Estrutura, estados e comportamento — nunca estética. Estado ausente é bloqueante; detalhe visual não vira finding.

Bloqueante

Merge negado. Devolve a tarefa para Bloqueado no plano.

Importante

Resolver agora ou na próxima tarefa, com a decisão registrada.

Sugestão

Opcional. Fica na mesa sem travar a entrega.

Filosofia

O que sustenta
o pipeline.

SDD pragmático, não ortodoxo. As divergências deliberadas com a literatura estão escritas no REFERENCES.md — discordar é mais fácil quando a fonte está na mesa.

Sai a coreografia, fica a verificação

Estado em fonte única, menos comandos e menos prosa. Gates, review independente e sensor de discriminação ficam intactos.

Granularidade não é qualidade

Quebrar em muitas tarefas compra ordem, não correção. A unidade é a fatia que fecha um cenário, medida por caber num ciclo.

Lacuna declarada vale mais que lacuna preenchida

Nenhuma skill inventa para fechar a matriz. Matriz honestamente incompleta é informação; matriz fechada com suposição é armadilha.

Stack-agnóstico no núcleo

Nenhuma skill traz tecnologia pré-definida. Exemplos com código real ficam isolados em stacks/, nunca misturados ao núcleo.

Sem cronograma, sem estimativa

O pipeline produz o quê, o porquê e em que ordem. Quando e quanto são responsabilidade do planejamento de sprint.

Português é padrão

Todos os artefatos saem em PT-BR. Termos técnicos consagrados podem ficar em inglês.

IA-friendly por design

IDs estáveis, pontos de validação humana explícitos e critérios de aceite testáveis — otimizado para ser consumido por agente.

Progressive disclosure

SKILL.md curta conduz a conversa. Os templates grandes ficam em references/, carregados só na hora de gerar o documento.

Instalação

Marketplace
local.

O plugin é distribuído internamente: o próprio repositório é o marketplace, adicionado por caminho local. Nada aqui depende de rede além do git clone.

Uso permanente

Para atualizar depois de um git pull, rodar claude plugin marketplace update leanwork. Hooks e scripts chamam python (3.8+), que precisa estar no PATH.

Desenvolvimento do plugin

A flag --plugin-dir carrega o plugin direto do diretório, sem instalar. Vale apenas pela sessão atual. 

# Uso permanente (equipe)
$ git clone https://github.com/leanwork/leanwork-sdd.git
$ claude plugin marketplace add ./leanwork-sdd
$ claude plugin install leanwork-sdd@leanwork

# Desenvolvimento do próprio plugin
$ claude --plugin-dir /caminho/para/leanwork-sdd

# Confirmar que as skills carregaram
> /plugin
